# 网盘品牌接入评估台账

记录**评估过但决定不接**的网盘品牌，以及否决理由和重新评估的触发条件。

目的：同一个需求被反复提出时，直接引用这里的结论和证据，不必重跑调研。

已接入的五个品牌（115 / 夸克 / 光鸭 / 123 / 天翼）不在此列，只在下面记一份资源量对比。

## 移动云盘（139 / 中国移动云盘，原「和彩云」）—— ❌ 不做（2026-08-23）

**需求来源**：issue #240（用户 `sjppppp` 自行接入后卡在转存失败）、#244 相关讨论

**结论**：不做。三条硬伤，任意一条都足以否决。

### 硬伤 1：转存成功后文件会被服务端删除 ⛔ 决定性

issue #240 作者的实测描述：

> 在移动云盘内也是能看到资源转存进来了，但是运行好久好久以后就把资源删除，回到后台就提示报错。

他用 AI 接入（粘贴 Authorization）+ 修了若干轮，症状不变。**问题不在代码层** —— 139 对影视类文件有事后审查。

外部佐证：NodeSeek [post-705635](https://www.nodeseek.com/post-705635-1) 同帖用户 `wulixi8`：

> 这云盘赛马娘都给我封了几集，不知道哪里违规了

**为什么这条是决定性的**：本产品的核心承诺是「转存后长期持有、缺集自动补齐」。一个会在数小时后删除内容的存储，追剧流程在语义上就跑不通 —— 巡检会反复发现「缺集」并反复转存，形成无限循环。

### 硬伤 2：139 官方不支持磁力离线

NodeSeek 帖子标题即结论：「移动云盘咋只能离线 http」。楼主 `nax`：

> 不能离线磁力就还是不行啊

本产品资源有两条腿：网盘分享链（PanSou）+ 磁力（Prowlarr）。139 只有 HTTP 离线，磁力这条腿直接断。

对比：115 / 夸克 / 123 均支持磁力离线，这是它们能进主线的前提。

### 硬伤 3：OpenList 的 139 驱动无转存能力

`OpenListTeam/OpenList` 有 `drivers/139`（注册名 `139Yun`，driver.go 1112 行 + meta/util，实现质量不低，登录做了 AES-CBC 三步握手）。

但分享模式（`Type: share`）**只读**。`driver.go` 有 8 处 `isShare()` 把关，`Copy()` 开头直接：

```go
func (d *Yun139) Copy(ctx context.Context, srcObj, dstDir model.Obj) error {
	if d.isShare() {
		return errs.NotImplement
	}
```

**它做的是「挂载」（列文件 → 拿直链 → 在线看），本产品要的是「转存」。** `packages/workflow/src/ports.ts` 的 `transfer()` 在该驱动上没有对应物。

社区信号：OpenList 仓库 139 相关 issue/PR 共 12 条，全部是登录 / 挂载 / 上传 / 容量计算，**零条涉及转存分享链**。这么活跃的项目都无人做成，说明该接口未公开或门槛极高。

### 资源覆盖率实测（自建 PanSou 实例，2026-08-23）

| 关键词 | 结果总数 | **mobile(139)** | quark | tianyi | 123 |
|---|---:|---:|---:|---:|---:|
| 海贼王 | 277 | **2** | 139 | 5 | 7 |
| 凡人修仙传 | 1323 | **8** | 270 | 7 | 56 |
| 猫和老鼠 | 338 | **0** | 154 | 6 | 0 |
| 合计 | | **10** | **563** | | |

PanSou 确实收录 139（type 名为 `mobile`），但量级差 **56 倍**，且「猫和老鼠」338 条结果中为 0。

issue #240 作者认为「一般热门资源还是有的」—— 偏乐观，但已非决定性因素。

### 成本参照

第五盘（天翼云盘）落地 commit `b48852d`：**43 文件 / +3605 行**，含 16 处需手动同步的注册点（`add-drive-brand-tabs.tsx` 单文件内即有 3 处品牌列表），另需手写该品牌的 agent prompt。

投入这个量级，换来：资源池 1/56 + 转存需从零实现 + 转存成功后被服务端删除。

### 重新评估的触发条件

同时满足才重启评估：

1. 139 官方支持磁力 / BT 离线下载
2. 不再对影视类文件做事后删除（或有稳定规避方式）
3. 出现可用的分享链转存实现（官方 API 或 OpenList 上游支持）

条件 2 是关键 —— 前两条不满足时，即使转存 API 出现也没有意义。

### 给提出者的替代方案

issue #240 作者弃用夸克的理由是「88vip 挂载使用速度慢和转码画质损失严重」。

这是**播放层**问题，非转存层：本产品转存的是原始文件，无任何转码；画质损失来自夸克自带播放器的在线转码。

绕开方式：
- OpenList/Alist 挂载夸克 → 直读原文件 → IINA / PotPlayer / Infuse 播放
- 或挂载后接 Emby / Jellyfin 建库

保留 88VIP 的空间与转存速度，仅将播放交给正经播放器，画质损失消失。其「自动追剧转存」需求用夸克现即可跑通。

## 百度网盘（`baidu`）—— ❌ 不做（2026-10-17）

**需求来源**：issue #323（用户 `Alex-wucxu` 询问是否可以支持百度网盘）

**结论**：不做。按准入清单逐项核查，在前三项（内容留存、磁力离线、分享链转存 API）和播放层体验上全部撞墙。

### 硬伤 1：官方开放平台无「分享链转存」接口，Web 私有转存带强风控验证码 ⛔ 决定性

- 百度网盘官方开放平台（`pan.baidu.com/rest/2.0/xpan/*`）仅提供自有网盘内的文件列举、移动、重命名、复制（`manage?method=copy`，仅限网盘内部路径复制）和分片上传，**不提供跨用户分享链接（`pan.baidu.com/s/...`）转存 API**。
- `OpenListTeam/OpenList` 的 `drivers/baidu_netdisk` 走的就是这套官方 `xpan` OAuth2 接口，**没有分享链转存能力，也没有 `baidu_share` 驱动**。
- 若强行逆向网页端私有接口（`/share/verify` 换 `BDCLND` + `/share/transfer` 带 `bdstoken`）：百度对高频/无人值守转存有极严的滑块/旋转图片验证码（`vcode`）风控，且 `BDUSS` / `STOKEN` 一旦异地或 Docker 容器无头请求极易触发二次验证掉线，无法满足后台定时巡检无人值守运行。

### 硬伤 2：磁力 / BT 离线下载名存实亡，且连 OpenList 都未实现

- `OpenList` 的 `baidu_netdisk` 驱动完全未实现 `OfflineDownload`。
- 百度网盘自身的磁力/BT 离线功能近年来对影视资源基本处于「任务长期卡 0% / 99% 或直接提示包含违规内容无法下载」的状态，无法承接 Prowlarr / PanSou 磁力通道。

### 硬伤 3：影视文件「8 秒温馨提示」和谐机制与非 SVIP 百 KB 级限速

- **内容留存**：百度网盘对热门院线电影、美剧、日漫有全网最严的哈希级审查，转存时完好、过后变成「8 秒净网温馨提示视频」是常态，直接触发「巡检或换源反复重下」的死循环。
- **非 SVIP 限速**：即使文件转存进盘，用户没有每年 ¥198~¥298 的 SVIP 会员时，挂载 WebDAV / 直链读取只有几十到一百 KB/s，根本无法用 Infuse / Kodi / IINA 流畅看 1080p/4K 原盘流。而有付费意愿的用户，115、夸克（88VIP 附赠）或 123 的自动化体验和秒传率远胜百度。

## 迅雷云盘（`xunlei`）—— ❌ 不做（2026-10-17）

**需求来源**：issue #319（用户 `OliverSparko` 希望支持迅雷网盘）

**结论**：不做。OpenList 现有三套驱动均无分享链转存，且其移动端伪装鉴权 + 验证码签名（`X-Captcha-Token`）+ 强版权和谐 + 非会员严苛配额，完全不适合作为无人值守媒体库后端。

### 硬伤 1：OpenList 无分享链转存实现，且鉴权依赖客户端设备签名与 `X-Captcha-Token` ⛔ 决定性

- 核查 `OpenListTeam/OpenList` 的 `drivers/thunder`、`drivers/thunder_browser`、`drivers/thunderx`：
  - **零分享链转存**：没有 `thunder_share` 驱动，`thunder/driver.go` 中仅有网盘内部 `Copy` 与 `OfflineDownload`，不支持把 PanSou 搜出的 `pan.xunlei.com/s/...` 分享链转存进盘。
  - **高危风控鉴权**：迅雷无公开 Web/OpenAPI，OpenList 的 `thunder` 驱动靠伪装安卓客户端（`Xiaomi_M2004j7ac` / `com.xunlei.downloadprovider`）、计算 `device_sign` / `creditkey`，并在每次请求头携带动态 `X-Captcha-Token`（验证码 token 过期报 error code `9`，Expert 模式甚至需要用户手填 `captcha_sign` 算法和 `refresh_token`）。这种逆向签名与人机验证高频变动，极易在后台定时任务中集体掉线。

### 硬伤 2：版权内容拦截与事后审查严重

- 迅雷对院线片、热门剧集有严格的版权黑名单（「应版权方要求无法下载/无法转存/违规内容」），不论是磁力离线还是云盘内留存，命中率和被封率都远高于 115 / 光鸭 / 123。

### 硬伤 3：同生态位已被 115 / 光鸭 / 123 + 夸克完全覆盖（YAGNI）

- 迅雷云盘的两个潜在卖点：
  1. **磁力离线**：本项目已支持 **115、光鸭、123** 三家原生磁力秒传/离线（上表 6 部作品磁力池 759 条，三家通吃），且迅雷非白金/超级会员每天云添加配额极低、普通用户取回速度被严苛限制。
  2. **分享链（PanSou `xunlei`）**：实测 6 部作品共 331 条，不到夸克（1679 条）的 **1/5**。
- 付出 ~40 文件 / 3000+ 行代码 + 持续跟进迅雷客户端风控签名对抗的维护成本，去接一个资源池只有夸克 1/5、磁力被 115/光鸭/123 完全覆盖、且随时因 `X-Captcha-Token` 失效瘫痪的网盘，完全违反 YAGNI。

## 附：新品牌接入的准入检查清单

从本次评估提炼。评估任何新网盘品牌前，按顺序验证 —— **任一项不通过即终止，不必继续**：

1. **内容留存**：转存后文件是否被服务端事后删除？（最容易被忽略，也最致命）
2. **磁力离线**：是否支持 magnet / BT？（决定能否接 Prowlarr 这条腿）
3. **分享链转存**：官方 API 或 OpenList 是否提供？注意区分「挂载」与「转存」
4. **资源覆盖率**：PanSou 实测多个关键词，与夸克同口径对比。参照线：天翼进主线时可用池 481 条
5. **成本**：约 40 文件 / 3000+ 行 / 16 处注册点

第 1 项排在最前，因为它无法用代码绕过，且在早期最难发现 —— issue #240 的作者是在「修了若干轮」之后才暴露这个现象的。
