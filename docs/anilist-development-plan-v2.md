## 二、项目背景

### 2.1 当前存在的问题

Mediary Scout 目前主要使用 TMDB 获取电影、电视剧和动画的元数据。

但日本动画存在一些特殊情况：

- TMDB 元数据更新可能不及时。
- 部分动画的续作没有独立季度条目。
- TMDB 与日本动画官方使用的季度划分可能不同。
- 部分动画使用连续集数，而不是按季度重新编号。
- 用户搜索具体动画续作时，可能无法选择正确的获取目标。

### 2.2 典型案例

《药屋少女的呢喃》第三季。

目前观察到：

- TMDB 页面将作品显示为第 1 季，共 60 集。
- 用户希望单独选择第三季。
- TMDB 的季度结构无法直接满足这一操作需求。
- 上游作者认为主要问题是搜索关键词和季度编号方式不同。

因此，问题不只是搜索字符串匹配，还涉及不同元数据平台对动画季度的组织方式。

**解决方向：保留 TMDB，同时新增 AniList，让用户能够选择更适合目标作品的元数据来源。**

注意：需要在正式开发时验证 AniList 对具体作品的收录情况，以及所选季度能否准确进入后续获取工作流。

## 三、核心架构

### 3.1 双元数据检索

保留原有 TMDB 搜索功能，新增 AniList Search Provider。

两个数据源独立运行：

| 数据源 | 主要用途 |
|---|---|
| TMDB | 电影、电视剧及原有动画检索 |
| AniList | 日本动画、续作、季度和播出信息 |

不使用 AI Agent 执行元数据搜索。

搜索由普通程序通过 API 请求完成。

### 3.2 搜索流程

```text
用户输入作品名称
        │
        ▼
    搜索页面
        │
        ├───────────────┐
        ▼               ▼
   TMDB API         AniList API
        │               │
        ▼               ▼
  TMDB Adapter     AniList Adapter
        │               │
        └───────┬───────┘
                ▼
        统一元数据格式
                │
                ▼
      按来源分别展示结果
                │
                ▼
       用户选择数据来源
                │
                ▼
      用户选择作品及季度
                │
                ▼
       获取任务兼容性校验
                │
                ▼
          提交获取任务
                │
                ▼
       原有 Worker / Agent
                │
                ▼
        资源检索与匹配
                │
                ▼
          夸克转存
                │
                ▼
        验证与状态更新
```

**核心原则：只扩展元数据检索与必要的任务适配，不改变 Agent 的执行模式。**

## 四、搜索页面设计

### 4.1 双来源独立展示

不强制合并 TMDB 和 AniList 搜索结果。

在现有搜索页面增加两个可切换的标签：

- TMDB 元数据
- AniList 元数据

例如搜索：

`药屋少女的呢喃`

用户可以自行切换结果来源。

**TMDB 标签：**

展示原有 TMDB 搜索结果及季度结构。

**AniList 标签：**

展示 AniList 收录的动画、续作及对应季度信息。

两个来源的数据互不覆盖。

这样可以避免因自动匹配不同平台作品而产生错误。

### 4.2 用户选择

用户需要能够：

1. 选择元数据来源。
2. 选择目标作品。
3. 选择需要获取的季度或集数范围（以该来源实际支持的数据为准）。
4. 点击原有「获取」按钮提交任务。

如果系统无法将所选目标安全转换为现有任务格式，则提示不兼容原因，不提交错误任务。

### 4.3 不重新开发搜索页面

保留现有：

- 搜索框
- 作品海报
- 作品详情
- 获取按钮
- 搜索结果展示结构
- 原有页面风格

只增加必要的数据源切换组件和元数据展示适配。

## 五、双 ID 设计

### 5.1 保留独立 ID

TMDB 与 AniList 使用不同的作品 ID。

分别保留：

- `tmdbId`
- `anilistId`

另外增加：

- `source`

例如：

```ts
type MediaIdentity =
  | {
      source: "tmdb";
      tmdbId: number;
    }
  | {
      source: "anilist";
      anilistId: number;
    };
```

### 5.2 ID 使用规则

当用户选择 TMDB 数据：

```json
{
  "source": "tmdb",
  "tmdbId": 12345
}
```

当用户选择 AniList 数据：

```json
{
  "source": "anilist",
  "anilistId": 67890
}
```

以上 ID 仅为格式示例，不是真实作品编号。

要求：

1. 不混用不同来源的 ID。
2. 不将 AniList ID 伪装成 TMDB ID。
3. 不要求不同平台使用相同编号。
4. 内部识别作品时使用来源与 ID 的组合。
5. 保留用户选择的原始数据来源。

**注意：以上为计划中的新接口格式，不代表 Mediary Scout 当前已经支持。**

## 六、元数据转译器设计

### 6.1 目标

新增轻量级元数据转译器：

**Metadata Adapter / Translator**

作用是将 TMDB 和 AniList 的元数据转换为统一的内部格式。

不使用大语言模型完成转译。

通过 TypeScript 的确定性代码实现。

### 6.2 统一数据结构

建议使用类似的数据模型：

```ts
type MediaSource = "tmdb" | "anilist";

type MediaIdentity =
  | { source: "tmdb"; tmdbId: number }
  | { source: "anilist"; anilistId: number };

type UnifiedMedia = MediaIdentity & {
  title: string;
  originalTitle?: string;
  aliases: string[];

  mediaType: "movie" | "tv" | "anime";

  year?: number;
  posterUrl?: string;

  season?: number;
  episodeCount?: number;
};
```

实际字段需要根据现有项目的类型定义调整。

### 6.3 主要职责

转译器只负责：

- 标准化标题字段。
- 标准化封面地址。
- 统一年份和媒体类型。
- 保留不同语言的作品名称。
- 保留作品来源及原始 ID。
- 规范化可用的季度、集数信息。
- 为获取任务提供必要的元数据。

### 6.4 不负责的事情

转译器不承担：

- 自动将所有 TMDB 和 AniList 作品合并。
- 猜测不明确的季度关系。
- 生成未经验证的 TMDB ID。
- 使用 AI 搜索元数据。
- 直接操作网盘。
- 自动执行转存任务。

避免把一个简单的数据适配器设计成复杂的元数据管理系统。

## 七、获取任务兼容设计

这是本次开发最重要的技术验证环节。

### 7.1 当前需要检查的问题

Mediary Scout 的现有工作流可能依赖：

- `tmdbId`
- TMDB 作品详情
- TMDB 季度信息
- 现有 `MediaSearchCandidate`
- 任务队列中的作品标识
- Agent 输入参数
- 数据库记录与追更状态

因此，仅在搜索结果中增加 `anilistId`，不一定能够直接提交获取任务。

### 7.2 兼容方案

建议增加轻量级任务适配层。

当用户提交获取任务时：

```text
用户点击获取
      │
      ▼
检查 source
      │
      ├── TMDB
      │     │
      │     ▼
      │  使用原有任务结构
      │
      └── AniList
            │
            ▼
       获取 AniList 元数据
            │
            ▼
       转换为统一业务目标
            │
            ▼
       检查原有工作流兼容性
            │
            ▼
        提交获取任务
```

目标是：

**无论用户选择 TMDB 还是 AniList，Agent 都尽量接收其原有工作流能够识别的业务目标。**

### 7.3 兼容边界

优先选择最小修改方案：

**方案 A：完全复用现有任务结构**

如果 AniList 元数据可以安全转换为现有任务目标，则直接使用原有流程。

**方案 B：最小扩展任务字段**

如果现有任务结构不能准确表达 AniList 独有的动画季度，则仅扩展必要字段及校验逻辑。

可能涉及：

- 来源标识
- AniList ID
- 作品别名
- 季度信息
- 经验证的集数映射

只在必要时修改任务入口、持久化或元数据读取接口。

不主动重构 Agent、Worker 或整个数据库结构。

### 7.4 特殊情况

如果 AniList 有某部动画的第三季，而 TMDB 没有独立第三季：

1. 允许用户在 AniList 结果中选择该季度。
2. 保留 AniList 原始作品 ID。
3. 检查能否生成现有系统接受的获取目标。
4. 如果存在可信的季度、集数映射，可以使用经过验证的映射。
5. 如果无法准确表达目标，则暂时禁止提交并提示原因。
6. 不将第三季错误地映射为 TMDB 的第一季全部内容。

**不能为了维持任务兼容性而牺牲获取结果的正确性。**

## 八、Agent 运行模式

### 8.1 保留现有架构

现阶段不修改：

- Agent 启动方式
- Worker 任务调度
- 原有资源搜索工具
- 资源匹配工作流
- 网盘转存机制
- 转存验证
- 自动追更与巡检模式

### 8.2 职责划分

**搜索模块：**

负责通过 TMDB / AniList 查找作品元数据。

**元数据转译器：**

负责数据标准化及来源识别。

**任务适配层：**

负责将用户选择的目标转换成可提交的获取任务。

**Agent：**

**Worker：**

继续负责现有任务执行与调度。

只有当实际测试证明原有 Agent 无法正确使用新增目标字段时，才考虑做必要的兼容调整。

## 九、热门动漫海报墙

Mediary Scout 当前搜索页面已经具有：

- 热门电影
- 热门剧集
- 热门动漫

因此，不需要重新开发海报墙。

### 9.1 数据来源调整

| 分类 | 数据来源 |
|---|---|
| 热门电影 | TMDB |
| 热门剧集 | TMDB |
| 热门动漫 | AniList |

### 9.2 AniList 榜单

计划展示：

- 当前季度动画
- 近期热门日本动画
- 即将播出的日本动画（根据实际 API 数据）
- 动画标题、海报、年份及热度信息

保持现有海报卡片布局。

点击 AniList 海报时，进入对应的 AniList 搜索或作品选择流程。

### 9.3 异常处理

当 AniList 请求失败时：

1. 优先使用有效缓存。
2. 必要时使用可用的历史缓存。
3. 没有可用数据时，可以回退到原有 TMDB 动漫榜单。
4. 不影响热门电影和热门剧集。
5. 不影响正常的作品搜索及资源获取。


## 十一、缓存与稳定性

### 11.1 API 缓存

为了避免高频请求 AniList：

- 为搜索结果设置合理缓存时间。
- 为作品详情设置缓存。
- 热门动漫榜单建议缓存 6–24 小时。
- 支持 API 超时和异常处理。
- 避免并发重复请求。

优先使用现有项目适合的缓存机制。

### 11.2 故障隔离

AniList 故障不能影响：

- TMDB 搜索
- 热门电影和剧集
- 原有获取任务
- Worker
- Agent
- 夸克网盘转存

### 11.3 数据正确性

保留来源 ID，禁止错误的季度映射。

对于不确定的作品关联或集数对应关系，优先要求用户确认，而不是自动推测。

## 十五、最终技术方案

**方案名称：**

Mediary Scout o0521 — TMDB + AniList 双元数据扩展

**总体结构：**

`双元数据检索 + 独立结果展示 + 双 ID + 轻量转译器 + 必要的任务适配 + 原有 Agent 工作流`

**核心目标：**

1. 保留 Mediary Scout 原有 TMDB 影视检索能力。
2. 增加 AniList 日本动画检索能力。
3. 允许用户独立选择 TMDB 或 AniList 的搜索结果。
4. 保留不同数据源的作品 ID，不产生编号混淆。
5. 将元数据转换为统一格式，尽量复用现有获取流程。
6. 保证正确识别目标作品及季度，不提交错误任务。
7. 保留原有 Agent、Worker、网盘转存和追更机制。
8. 将热门动漫海报墙的数据源调整为 AniList。
9. 尽可能降低二次开发代码与上游项目的冲突。

### 最终开发原则

**只扩展元数据入口，不主动改造 Agent 的运行机制。**

AniList 负责提供更多动画元数据，转译器负责处理不同平台的数据格式，任务适配层负责必要的兼容处理。

是否需要修改任务结构，取决于正式开发前的源码检查与实际测试结果。
